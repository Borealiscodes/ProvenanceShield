# 📊 ProvenanceShield Forensic Log Ledger Specification v3.0

This specification details the immutable structural constraints, field definitions, and cryptographic chaining sequence governing the output generated by `secure_logging.py`. Every log file must adhere strictly to this format to maintain courtroom eligibility under international digital evidence preservation guidelines (such as ISO 27037).

---

## ⛓️ 1. The Sequential Cryptographic Chain Definition

The forensic ledger is maintained as a sequential append-only line-delimited JSON document. For any given log line N (where N > 0), the validity of the chain is cryptographically bound to block N-1 via the following recursive structural relationship:

\[\text{Block}_{N}(\text{previous\_block\_hash}) = \text{Hash}(\text{Block}_{N-1})\]

If an administrative adversary truncates historical blocks, deletes lines, or alters internal payload metrics, the sequence breaks immediately. Any block displaying an unverified hash link must be treated as structurally compromised.

---

## 📐 2. Mandatory Structural JSON Schema

Every block must be serialized as a single-line JSON object utilizing alphabetical key sorting (`sort_keys=True`) to guarantee stable byte evaluations. The schema contains the following fields:

| Field Key | Primitive Type | Architectural Purpose |
| :--- | :--- | :--- |
| `collection_method` | `String` | Hardcoded assertion tracking local collection provenance. |
| `current_block_hash` | `String (Hex)` | The definitive SHA-256 hash of the entire current block object. |
| `current_custodian` | `String` | Tracks the automated data intake software layer. |
| `device_context` | `Object` | Captures the hardware environment parameters at the millisecond of capture. |
| `device_context.enclave_active` | `Boolean` | True if the memory isolation perimeter was verified at runtime. |
| `device_context.hardware_mrenclave` | `String (Hex)` | The physical boot hash of the software code extracted from the silicon. |
| `device_context.host_id` | `String` | The unique identifier tracking the isolated Confidential VM space. |
| `device_context.os_platform` | `String` | The system identifier profile tracking kernel state. |
| `operational_purpose` | `String` | Fixed context string mapping compliance validation goals. |
| `previous_block_hash` | `String (Hex)` | The SHA-256 signature hash extracted from the tail of the preceding line. |
| `rfc3161_timestamp_token` | `String (Base64)` | The DER-encoded signature block issued by an external timestamp authority. |
| `telemetry_payload_hash` | `String (Hex)` | The standalone SHA-256 hash of the target human rights telemetry input. |
| `unix_time` | `Float` | The local epoch timestamp recording the injection event context. |

## 🔍 4. Verification Auditing Checklist for Human Rights Tribunals

When presenting this log file to international panels, investigators must verify compliance against this strict checklist:
1. **Genesis Initialization:** Confirm that row 0 carries a `previous_block_hash` value consisting entirely of 64 consecutive `0` characters.
2. **Hash Continuity:** Run a sequential parsing loop ensuring that the `current_block_hash` of entry N perfectly populates the `previous_block_hash` field of entry N+1.
3. **MRENCLAVE Validation:** Cross-reference the value inside `device_context.hardware_mrenclave` against the open-source compilation manifest (`provenance_manifest.json`) generated by the deterministic build pipeline to confirm the telemetry wasn't processed by a corrupted or modified script variant.
